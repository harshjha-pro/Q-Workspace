# Technical decisions (brief rule 9: decided by the engineer, recorded here)

Status: D-01…D-25 accepted with the plan (6 Oct 2026); D-26–D-37 added during Phase 1; D-38 onwards during Phase 2. Amended rows say so.

| ID | Decision | Why |
|---|---|---|
| D-01 | Single Next.js process serves staff, admin and portal route groups; no separate API server | Zero-setup; one `npm run dev` |
| D-02 | SQLite in WAL mode, file at `prisma/data/qepex.db`; `busy_timeout` 5 s | Concurrent readers + one writer is ample for a ~25-person firm on a LAN |
| D-03 | Enums stored as `String` + Zod/TS unions; no Prisma `enum`, no `Json` columns (JSON stored as validated `String`) | Identical behaviour on SQLite and PostgreSQL |
| D-04 | Money in integer paise; hours in integer minutes; business dates as `YYYY-MM-DD` strings in IST | No float errors; no timezone off-by-one on due dates |
| D-05 | Task natural key = `(clientId, complianceTypeCode, partyKey, periodKey)`, unique index. `partyKey` = GSTIN id (GST types), Director id (DIR-3 KYC — one task per director, attached to `Director.primaryClientId` and listed on every linked company), PT state code (Professional Tax), `-` otherwise | Supports per-GSTIN and per-director obligations (Spec §4.1) while keeping Rules Spec §3.3 idempotency |
| D-06 | Compliance engine is pure (no Prisma, no clock); `today` injected; service layer persists plans in one transaction | 100% branch coverage is practical; scenario tests run in milliseconds |
| D-07 | Stored statuses are exactly the 7 in the spec. "Overdue", "At Risk", "Due today" are derived at read time from status + effective due date + budget band | Rules Spec §8 says status is computed; avoids a status the spec does not define |
| D-08 | A PendingRecord links specific checklist items; the task reverts to In Progress when all linked items are Received *and confirmed*, or when manually cleared | Makes "the relevant item" (Rules §8) precise; respects staff confirmation of portal uploads |
| D-09 | Auth.js v5 credentials provider; the JWT carries only a `UserSession` row id. Every request re-validates that row (not revoked, not past absolute expiry, not idle > 30 min, user still active) and touches `lastSeenAt` at most once a minute. *(Amended in Phase 1: a session table instead of a bare `sessionEpoch`, because idle timeout needs server-side last-seen.)* | Credentials provider needs JWT; DB check gives idle timeout and immediate revocation at offboarding/role change/password reset |
| D-10 | Two AES-256-GCM keys: `VAULT_KEY` (credentials) and `PII_KEY` (salary, bank, Aadhaar, employee PAN); ciphertext prefixed with key version | Spec §14.4 asks for separate keys; versioning allows rotation |
| D-11 | Full-text search via a portable `DocumentSearchToken` table (tokenised on upload for text/PDF text/Office text) behind a `SearchService` interface | SQLite FTS5 is not portable to PostgreSQL |
| D-12 | node-cron started from `instrumentation.ts` with a global guard; every job idempotent, logged to `JobRun`, with Run now and catch-up on boot | Laptop may sleep through a schedule |
| D-13 | Service worker hand-written (no Workbox/Serwist); the offline queue uses IndexedDB directly with a localStorage fallback (no `idb` package, so no new dependency); offline entries carry a client UUID for idempotent sync. *(Amended in Phase 2: `idb` was not needed.)* | Small surface; only one offline flow |
| D-14 | `docx` npm package for Word output of templates/letters; `@react-pdf/renderer` for all PDFs; `exceljs` for all Excel | Spec §13.3 requires Word output; all pure JS, no services |
| D-15 | `npm run dev` / `npm start` bind 127.0.0.1; `npm run dev:lan` / `start:lan` bind 0.0.0.0 for phones on the office Wi-Fi. *(Amended: separate scripts instead of an env flag — works the same on Windows.)* | Safe by default; see open question Q-26 on HTTPS for LAN use |
| D-16 | Firm's own one-off obligations (COP, PI insurance, peer review, licences) use compliance types with a `MANUAL` due-date rule (date typed per instance) | Reuses the engine (Spec §13.6) without inventing statutory dates |
| D-17 | Statutory values (due dates, late fees, interest, PF/ESI/PT, tax slabs, stipend minimums, CPE hours) are seeded as rows with `source`, `effectiveFrom`, `verifiedBy = null`. The Due-Date Master and Statutory Settings pages show an "Unverified" badge until a Partner marks each row verified | Brief rule 5; specs mark every value illustrative |
| D-18 | Review levels per stage come from the stage template (`reviewLevel: NONE|SENIOR|MANAGER|PARTNER`); "Senior" = Staff user with `isSenior` (not an eighth role) | Spec has seven roles; §3.3 says Seniors may review |
| D-19 | Correction requests on a Manager's own entries go to their reporting Partner; on a Partner's own entries to any other Partner | Nobody approves their own correction |
| D-20 | Audit log is append-only at the code level (no update/delete functions exported); before/after stored as JSON diff | Spec §5.7 |
| D-21 | Portal invite tokens: 32 random bytes, stored as SHA-256 hash, single use, 7-day expiry (setting) | Invite link replaces OTP delivery |
| D-22 | Backup = `VACUUM INTO` snapshot + `/storage` zipped with SHA-256 manifest. Restore: verify manifest → automatic PRE_RESTORE backup → bring the backup DB to the current schema with `migrate deploy` → copy its rows into the live DB through SQLite `ATTACH` in one batch → swap the storage folder. *(Amended: the live DB file is never replaced on disk — a disconnected Prisma/libsql client keeps the old file handle open, which locked the DB in testing.)* | Consistent snapshot; restore works while the app is running |
| D-23 | Uploads: allow-list (pdf, jpg, png, xlsx, xls, csv, docx, doc, zip, txt, json, xml), magic-byte check, 25 MB default (setting), stored under random names | Replaces virus scanning (brief §4) |
| D-24 | UI: shadcn/ui on Tailwind with one status-colour map shared by every list, calendar and board | Brief §10 "same status colours everywhere" |
| D-25 | Fake identifiers in seed follow real formats with valid check characters where one exists (GSTIN checksum), PAN pattern `AAAAA9999A`, DIN 8 digits, UDIN 18 characters | Brief §12 |
| D-26 | Audit columns (`createdById`, `updatedById`) and most "who" fields are plain indexed ids, not Prisma relations; relations are declared for the core chains (client → GSTIN/director/engagement/task, engagement → task, task → children, user → entries/assignments) | Keeps 181 models readable; referential integrity where it matters |
| D-27 | Prisma 7 with the `@prisma/adapter-libsql` driver adapter (prebuilt binaries via npm, no compiler or GitHub download needed); multi-file schema in `prisma/schema/` | Zero-setup install on Windows/macOS/Linux |
| D-28 | Updates go through `parsePartial()`: only keys actually sent are applied | Zod's `.partial()` still applies `.default()`s, which silently reset untouched fields (found and fixed in Phase 1) |
| D-29 | Only a Partner may grant or take away the Partner, Practice Admin and HR Admin roles (create, change, reset, deactivate such users) | These roles control money, people and configuration |
| D-30 | Everyone can read their own employee record and documents, whatever their role's HR scope | Spec 3.3 "own"; Practice Admin otherwise had no access to their own record |
| D-31 | HR Admin runs exits but sees client-linked custody items (documents, engagements, tasks) as counts, not names | Spec 3.6: HR has no client data |
| D-32 | Fee basis, fee, rate and chargeable flag on an engagement can be set at creation by its Manager, but changed afterwards only by a Partner (service-enforced) | Spec 3.1/7.1: Partners approve fees and chargeability |
| D-33 | Restore approval: a Practice Admin's request needs a Partner; a Partner may confirm their own request after typing RESTORE | Spec 14.5 Partner approval; single-Partner firms must still be able to restore |
| D-34 | Next.js telemetry is disabled by `npm run setup` (`next telemetry disable`) and `agentRules: false` stops Next writing AGENTS.md/CLAUDE.md | Nothing leaves the machine (brief §4) |
| D-35 | TanStack Table pinned to v8 (v9 has a different API); React Hook Form + Zod resolver for the client form; simple forms use server actions with `useActionState` | Stable APIs; less client code for small dialogs |
| D-36 | Demo users in roles with mandatory 2FA share one documented authenticator secret (`npm run demo:totp` prints the code); real users enrol their own | Keeps 2FA real in the demo without a phone per role |
| D-37 | `package.json` `overrides` pin patched versions of three transitive packages (`uuid` under exceljs; `mysql2` and `deepmerge-ts` under the Prisma CLI); `npm audit --omit=dev` reports 0 vulnerabilities | Fix known advisories without downgrading Prisma or ExcelJS; tests confirm both still work |
| D-38 | Credentials vault visibility: Partners and Practice Admin firm-wide; Managers for their team's clients; Staff and Articles only with a live `CredentialGrant` **and** a current assignment on that client (Q-06). Grants can only be given to people assigned to the client. Every reveal writes `CredentialViewLog` and `SensitiveViewLog`; secrets never enter the audit trail | Q-06 "only when they are assigned"; spec 6.4 |
| D-39 | Backups are sealed with AES-256-GCM using `BACKUP_KEY` from `.env` (file extension `.qbk`, header `QEPEXBK1`); setup generates the key; plain `.zip` backups from before still restore. Restoring on another computer needs the same `.env` | Q-27 |
| D-40 | HTTPS on the office network uses one self-signed certificate per computer (`selfsigned`, MIT, ~60 kB), generated into `certs/` (git-ignored) for its hostname and LAN IPs, valid 825 days, flagged as a CA so phones can install it as trusted. `npm run start:lan:https` serves the build; `dev:lan:https` uses Next's own HTTPS dev mode with the same cert | Q-26; service workers (offline entry) need a secure origin on phones |
| D-41 | An extension with "all open periods" applies to every period of the chosen types (within the scope clauses) that is still open, plus Filed Late tasks filed on or before the new date, which become Filed; Filed tasks never move. Publishing requires confirming the affected count shown in the preview, and an extension is corrected only by publishing a superseding one | Rules Spec 5 (extensions); prevents a mistaken blanket shift |
| D-42 | Period inclusion: a period is generated when its end ≥ obligation start and its start < obligation end; event-offset obligations (e.g. AOC-4 after AGM) only after the FY closes; generation horizon is current + next period (months: +2) | Rules Spec 4 read literally; avoids tasks for periods the client was not liable for |
| D-43 | Auto-generated tasks do not notify anyone on creation; people hear about them through the 7/3/1-day reminders and the Due This Week strip | Hundreds of tasks appear at setup and every month; creation alerts would drown the useful ones |
| D-44 | Weekly lock is evaluated at read time (Sunday at `work.weeklyLockTime` IST of the entry's week) rather than by a job; Partner extensions are `WeeklyLock` rows for the firm or one person with an end time | No job to miss when the laptop sleeps; extensions are explicit and audited |
| D-45 | Reminder cadence (7/3/1 days, escalation after 1 and 3 days, pending follow-up every 3 days, review SLA 2 days) is held in settings `reminders.*`, defaulting to Rules Spec 9 | Firm policy, not statute — admin-editable |
| D-46 | Exports run through the same record scopes as the screens and are written to `ExportJob` + audit; CSV cells starting with `= + - @` are prefixed with `'` and files carry a UTF-8 BOM | Nobody exports what they cannot see; formula-injection safe in Excel |
| D-47 | Stage-template edits create a new version (draft → Partner publishes). Publishing either leaves open tasks on their version or moves them with an explicit old-stage → new-stage mapping for every stage that has open tasks | P2-24; no silent stage jumps |
| D-48 | Applicability flags given when a client is created apply from its onboarding date, or, when that is blank, from `compliance.trackingFrom` (never later than today). Changes made afterwards keep their own effective dates | An existing client brought into the app has been liable all along; dating its flags "today" dropped current-year filings for earlier periods (found in the go-live rehearsal) |
| D-49 | Go-live cut-off `compliance.createDueFrom`: generation skips tasks whose computed due date is before it; tasks without a date (manual due dates) are still created. Re-runs stay idempotent | Q-32: work already due before go-live was handled outside the app and must not appear as overdue |
| D-50 | Office holidays = national + firm holidays + state holidays of the firm profile's state (Rajasthan). They drive leave days, missing-entry checks, the week grid and the calendar, never statutory due dates | Q-31 |
| D-51 | Engagements import (Partner only, like engagement fees, D-32): client matched by code, PAN or exact name; a recurring row updates the client's existing active recurring engagement of the same type instead of duplicating it; makers/checkers flow to open tasks through the normal assignment rules | Go-live (Q-32): staffing ~150 engagements by hand was not practical |
| D-52 | Due-date rules and late-fee rates can be verified by the Practice Admin or a Partner | Q-29 |
